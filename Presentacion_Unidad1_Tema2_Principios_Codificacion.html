2.1 Principios de Preparación

¿Qué son los Principios de Preparación?

Imagina que vas a cocinar un platillo complejo. Antes de encender la estufa, necesitas: leer la receta completa, reunir todos los ingredientes, preparar los utensilios y organizar tu espacio de trabajo. Los principios de preparación en programación funcionan de la misma manera: son todas las actividades que realizamos antes de escribir la primera línea de código.

📋

Planificación del Código

¿Por qué planificar?
Programar sin planificación es como construir una casa sin planos. Incluye:
• Comprensión del problema
• Diseño previo
• Definición de estándares
• Configuración del entorno

⚙️

Análisis de Requerimientos

Condiciones especiales:
• Rendimiento: ¿Qué tan rápido debe responder?
• Seguridad: ¿Qué datos son sensibles?
• Compatibilidad: ¿En qué sistemas debe funcionar?
• Tecnologías: ¿Qué herramientas usar?

2.2 Principios SOLID

Las "Reglas de Oro" para escribir buen código

Los principios SOLID son como las reglas de etiqueta para el código. Cada letra representa una regla fundamental.

S

Single Responsibility

Una sola responsabilidad:
Cada clase debe hacer una sola cosa y hacerla bien.

Analogía: Un cuchillo corta, un tenedor pincha. No harías un "cuchillo-tenedor-cuchara".

O

Open/Closed

Abierto para extensión, cerrado para modificación:
Debes poder agregar nuevas funcionalidades sin cambiar el código existente.

Analogía: Como las apps que instalas sin modificar el sistema operativo.

L

Liskov Substitution

Sustitución sin romper nada:
Las clases hijas deben poder reemplazar a las clases padre sin problemas.

Analogía: Un control remoto debe funcionar con cualquier TV de esa marca.

I

Interface Segregation

No forzar métodos innecesarios:
No obligues a una clase a implementar métodos que no va a usar.

Ejemplo: Interface separadas para trabajadores y seres vivos.

D

Dependency Inversion

Depender de abstracciones:
Las clases importantes deben depender de interfaces, no de implementaciones concretas.

Analogía: Un enchufe permite conectar cualquier aparato eléctrico.

S - Single Responsibility Principle

Cada clase debe tener una sola razón para cambiar

Una clase debe hacer una cosa y hacerla bien. Si una clase tiene múltiples responsabilidades, cambios en una pueden afectar a la otra.

❌ Malo - Múltiples Responsabilidades

class Usuario: def __init__(self, nombre, email): self.nombre = nombre self.email = email # Responsabilidad 1: Gestionar datos def obtener_nombre(self): return self.nombre # Responsabilidad 2: Enviar emails def enviar_email(self, mensaje): print(f"Enviando a {self.email}: {mensaje}") # Responsabilidad 3: Guardar en BD def guardar_en_db(self): print(f"Guardando {self.nombre} en BD")

✅ Bueno - Una Responsabilidad

class Usuario: def __init__(self, nombre, email): self.nombre = nombre self.email = email def obtener_nombre(self): return self.nombre class EmailService: def enviar(self, usuario, mensaje): print(f"Enviando a {usuario.email}: {mensaje}") class UsuarioRepository: def guardar(self, usuario): print(f"Guardando {usuario.nombre} en BD")

🎯 Beneficios

• Mantenibilidad: Cambios en email no afectan datos de usuario
• Reutilización: EmailService puede usarse con otras clases
• Testing: Cada clase se puede probar independientemente

O - Open/Closed Principle

Abierto para extensión, cerrado para modificación

Debes poder agregar nuevas funcionalidades sin modificar el código existente. Usar abstracciones para esto.

❌ Malo - Modificar código existente

class CalculadoraDescuento: def calcular(self, precio, tipo_cliente): if tipo_cliente == "regular": return precio elif tipo_cliente == "premium": return precio * 0.9 elif tipo_cliente == "vip": # Nuevo! return precio * 0.8 # Modificando else: return precio # Para agregar nuevo tipo, hay que modificar la clase

✅ Bueno - Extensible sin modificar

from abc import ABC, abstractmethod class EstrategiaDescuento(ABC): @abstractmethod def aplicar(self, precio): pass class DescuentoRegular(EstrategiaDescuento): def aplicar(self, precio): return precio class DescuentoPremium(EstrategiaDescuento): def aplicar(self, precio): return precio * 0.9 class DescuentoVIP(EstrategiaDescuento): # Nuevo! def aplicar(self, precio): # Sin modificar return precio * 0.8 # código existente class CalculadoraDescuento: def calcular(self, precio, estrategia): return estrategia.aplicar(precio)

🎯 Beneficios

• Sin riesgo: No rompes código existente al agregar funcionalidad
• Flexibilidad: Fácil agregar nuevos tipos de descuento
• Mantenimiento: Cada estrategia es independiente

L - Liskov Substitution Principle

Las clases hijas deben poder sustituir a sus padres

Si tienes una clase padre, cualquier clase hija debe poder usarse en su lugar sin romper el programa.

❌ Malo - Viola LSP

class Rectangulo: def __init__(self, ancho, alto): self.ancho = ancho self.alto = alto def area(self): return self.ancho * self.alto class Cuadrado(Rectangulo): def __init__(self, lado): super().__init__(lado, lado) # Problema: comportamiento inesperado def set_ancho(self, ancho): self.ancho = ancho self.alto = ancho # Rompe expectativa! # Esto funciona mal: def probar_rectangulo(rect): rect.set_ancho(5) rect.set_alto(4) # Esperamos área = 20, pero cuadrado dará 16!

✅ Bueno - Respeta LSP

from abc import ABC, abstractmethod class Forma(ABC): @abstractmethod def area(self): pass class Rectangulo(Forma): def __init__(self, ancho, alto): self.ancho = ancho self.alto = alto def area(self): return self.ancho * self.alto class Cuadrado(Forma): def __init__(self, lado): self.lado = lado def area(self): return self.lado * self.lado # Ambas se pueden usar igual: def calcular_area_total(formas): return sum(forma.area() for forma in formas)

🎯 Beneficios

• Predictibilidad: Las clases hijas se comportan como esperamos
• Polimorfismo seguro: Puedes usar cualquier subclase sin sorpresas
• Confiabilidad: El código es más robusto y confiable

I - Interface Segregation Principle

Interfaces específicas son mejores que una general

No fuerces a una clase a implementar métodos que no necesita. Mejor divide en interfaces pequeñas y específicas.

❌ Malo - Interface muy grande

from abc import ABC, abstractmethod class Trabajador(ABC): @abstractmethod def trabajar(self): pass @abstractmethod def comer(self): # ¿Y los robots? pass @abstractmethod def dormir(self): # ¿Y los robots? pass class Robot(Trabajador): def trabajar(self): print("Robot trabajando") def comer(self): pass # No come, pero obligado a implementar def dormir(self): pass # No duerme, pero obligado a implementar

✅ Bueno - Interfaces segregadas

from abc import ABC, abstractmethod class Trabajador(ABC): @abstractmethod def trabajar(self): pass class SerVivo(ABC): @abstractmethod def comer(self): pass @abstractmethod def dormir(self): pass class Humano(Trabajador, SerVivo): def trabajar(self): print("Humano trabajando") def comer(self): print("Humano comiendo") def dormir(self): print("Humano durmiendo") class Robot(Trabajador): # Solo implementa lo que necesita def trabajar(self): print("Robot trabajando")

🎯 Beneficios

• Flexibilidad: Cada clase implementa solo lo que necesita
• Claridad: Interfaces específicas son más fáciles de entender
• Mantenimiento: Cambios en una interface no afectan otras

D - Dependency Inversion Principle

Depende de abstracciones, no de implementaciones concretas

Las clases de alto nivel no deben depender de clases de bajo nivel. Ambas deben depender de abstracciones.

❌ Malo - Dependencia directa

class EmailSender: def enviar(self, mensaje, destinatario): print(f"Email enviado a {destinatario}: {mensaje}") class NotificacionService: def __init__(self): # Dependencia directa de EmailSender self.email_sender = EmailSender() def notificar(self, mensaje, usuario): # Solo puede enviar emails self.email_sender.enviar(mensaje, usuario.email) # Problema: Para agregar SMS hay que modificar la clase

✅ Bueno - Depende de abstracción

from abc import ABC, abstractmethod class NotificationSender(ABC): @abstractmethod def enviar(self, mensaje, destinatario): pass class EmailSender(NotificationSender): def enviar(self, mensaje, destinatario): print(f"Email enviado a {destinatario}: {mensaje}") class SMSSender(NotificationSender): def enviar(self, mensaje, destinatario): print(f"SMS enviado a {destinatario}: {mensaje}") class NotificacionService: def __init__(self, sender: NotificationSender): # Depende de abstracción self.sender = sender def notificar(self, mensaje, destinatario): # Puede usar cualquier implementación self.sender.enviar(mensaje, destinatario) # Uso flexible: email_service = NotificacionService(EmailSender()) sms_service = NotificacionService(SMSSender())

🎯 Beneficios

• Flexibilidad: Fácil cambiar implementaciones sin modificar código
• Testing: Puedes usar mocks para probar
• Reutilización: El mismo servicio funciona con diferentes implementaciones

Clean Code - Código Limpio

¿Qué es el código limpio?

Es código que se lee como un libro bien escrito: claro, fácil de entender y sin ambigüedades.

❌ Malo

def calcular(): d = 5 # ¿d de qué? return d * 1.21

✅ Bueno

def calcular_precio_con_iva(): precio_base = 5.00 IVA = 1.21 return precio_base * IVA
📝

Nombres Significativos

Regla de oro: Si necesitas un comentario para explicar qué hace una variable, el nombre no es bueno.

🔧

Funciones Pequeñas

Máximo 20 líneas: Es más fácil entender y probar una función que hace una cosa simple.

💬

Comentarios Necesarios

El código debe explicarse por sí mismo. Solo comenta el "por qué", no el "qué".

⚠️

Manejo de Errores

Sé específico: Captura errores específicos y registra información útil para el debug.

Ejemplo Práctico: Código Limpio en Python

user_validator.py
# Ejemplo de código limpio - Python 3.12 import re from dataclasses import dataclass from typing import List @dataclass class ValidationResult: is_valid: bool errors: List[str] class UserValidator: MIN_AGE = 18 EMAIL_PATTERN = r'^[A-Za-z0-9+_.-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$' def validate_user(self, user) -> ValidationResult: errors = [] self._validate_age(user.age, errors) self._validate_email(user.email, errors) return ValidationResult(len(errors) == 0, errors) def _validate_age(self, age: int, errors: List[str]) -> None: if age < self.MIN_AGE: errors.append("Usuario debe ser mayor de edad") def _validate_email(self, email: str, errors: List[str]) -> None: if not re.match(self.EMAIL_PATTERN, email): errors.append("Formato de email inválido")

¿Qué hace que este código sea limpio?

• Nombres descriptivos: UserValidator, validate_user, MIN_AGE
• Funciones pequeñas: Cada método tiene una responsabilidad específica
• Type hints: Especifica tipos para mejor documentación
• Constantes: MIN_AGE y EMAIL_PATTERN son fáciles de modificar
• Separación de responsabilidades: Validación de edad y email por separado

2.3 Principios de Despliegue

¿Qué son los Principios de Despliegue?

Son las reglas para "poner en funcionamiento" tu software en el mundo real. Es como la diferencia entre cocinar en tu casa (desarrollo) y servir en un restaurante (producción): necesitas procesos más rigurosos.

🚀

Preparación para Producción

• Configuration Management: Separar configuración del código
• Variables de entorno: Información sensible fuera del código
• Health Checks: URLs que verifican el estado de la app
• Logs estructurados: Para análisis automatizado

🔄

DevOps Básico

• Continuous Integration: Integrar cambios automáticamente
• Continuous Deployment: Desplegar si las pruebas pasan
• Infrastructure as Code: Describir infraestructura con código
• Monitoring: Vigilar que todo funcione

📦

Containerización

¿Qué es un contenedor?
Una "caja" que incluye tu aplicación y todo lo necesario para funcionar.

Beneficios: Consistencia, aislamiento, escalabilidad

🔒

Seguridad Básica

• HTTPS obligatorio: Encriptar comunicación
• Gestión de secretos: Contraseñas fuera del código
• Actualizaciones: Parches de seguridad constantes
• Acceso mínimo: Solo lo necesario
